# A local, vault-gated dev log

**Status:** Complete.
**Roadmap reference:** None. This is developer/debugging tooling requested directly by the user, not tied to any `docs/roadmap.md` phase objective — recorded here (rather than left undocumented) so it isn't mistaken for missing scope from an existing phase.
**ADR:** [`../adr/ADR-019-local-log-gated-by-vault-auth.md`](../adr/ADR-019-local-log-gated-by-vault-auth.md) covers the access-control design decision in full; this doc covers the rest of the implementation.

## Context

Running the extension locally surfaced a need for a persisted record of internal errors/debug events (e.g. what actually happened around a failed background operation) without opening a devtools console at the exact right moment. The user asked for: an on/off toggle (default on), some access control since the content could be worth protecting, and an extra re-confirmation step specifically before exporting the log file to disk. See ADR-019 for why access control ended up reusing the vault's own authentication instead of a bespoke password scheme.

**Follow-up expansion** (same feature, second pass): the original 5 call sites were all error-catch branches with a plain on/off toggle. A second round of work turned this into an actual tracing tool: a 3-way verbosity threshold (`off`/`info`/`debug`, replacing the boolean), content-script coverage (previously unreachable from the persisted log entirely), and `'info'`/`'debug'`-level tracing along the Content Script → dispatch → Policy Engine → Firewall flow `docs/architecture.md`/`docs/browser-architecture.md` describe — see "Design decisions (verbosity + tracing)" below.

## Design decisions

- **On/off toggle** (superseded — see below): `AppSettings.logsEnabled: boolean`, default `true` (`shared/settings.ts`) — exactly like the existing `autoLockSeconds`/`credentialSaveMode` fields. Adding this required field means any already-stored `AppSettings` blob predating it fails schema validation as a whole and falls back to `DEFAULT_APP_SETTINGS` — a one-time settings reset accepted deliberately (CLAUDE.md's "no compatibility layers for what's obsolete"), not a migration system, since this is a personal project with no external users yet.
- **Viewing** is gated by `VaultLockedNotice` inside the Configuration tab's own "Logs" card (not the whole tab — the rest of Configuration stays usable while locked, per ADR-018).
- **Clearing** only needs the vault unlocked (no extra re-confirmation — it deletes data, it doesn't expose it).
- **Exporting** re-confirms via an inline passphrase/passkey form before the actual file download runs (ADR-019).
- **Export format**: plain, human-readable text (one entry per line: timestamp, level, message, detail) — a debug log meant to be read directly, not a data-interchange format. Filename: `identity-firewall-logs-<timestamp>.log`.
- **Storage**: capped ring buffer, 500 entries, plain `browser.storage.local` (key `if_logs_v1`) — no IndexedDB, no new library, matching the user's own explicit "no overengineering" request and this codebase's own convention that every same-sized concern under `background/` splits into `storage.ts` + `handler.ts`.
- **The Logs card shows the actual entries live**, not just a count — a scrollable, newest-first list (capped to the most recent 100 rendered, well below the 500-entry backend cap, to keep DOM size cheap in a perpetually-open Options tab), colored by level using `theme.css`'s own real palette rather than Tailwind's generic `red-600` (see the 3-way color mapping below). "Live" is `browser.storage.onChanged` (first use of this API anywhere in the codebase): the Options page listens for any `'local'`-area storage change and refetches `GET_LOGS`, rather than a new dedicated `LOGS_CHANGED` message — deliberately not filtered to the log's own storage key, since that key is a background-private implementation detail (ADR-019) this component has no reason to duplicate, and refetching on any local-storage write is cheap enough not to need that precision.

## Design decisions (verbosity + tracing)

- **`AppSettings.logsEnabled: boolean` → `AppSettings.logLevel: 'off' | 'info' | 'debug'`** (`shared/settings.ts`, `LogThresholdSchema`). Same settings-reset consequence as any other `AppSettingsSchema` field change (accepted, no migration system). Default **`'debug'`**, not `'info'` — preserves the exact behavior the old `logsEnabled: true` default already had (persisting everything that existed at the time); defaulting quieter would have silently hidden the new tracing this was built for. Semantics, a straight 3-branch ladder with no special-casing: `'off'` persists nothing (including `'error'`-tagged entries — this purely gates persistence, matching ADR-019's "no exceptions" invariant), `'info'` persists `'info'`+`'error'`, `'debug'` persists everything. Console output is unconditional regardless of threshold, unchanged from before.
- **`LogEntry.level` (`shared/messages.ts`) gained a third tag, `'info'`**, alongside the original `'debug'`/`'error'` — now schema-first (`LogLevelSchema = z.enum([...])`) rather than a bare TS union, since `RECORD_LOG_ENTRY` below needs real Zod validation for it.
- **Content script coverage via a new `RECORD_LOG_ENTRY` message.** A content script is a separate JS execution context (ADR-011) with no access to `background/logging/handler.ts`'s module — mirroring `GET_LOGS`/`CLEAR_LOGS`'s simplicity, `content/log.ts`'s `reportLog(level, message, detail?)` fire-and-forget sends `RECORD_LOG_ENTRY`, which `background/logging/handler.ts`'s `handleRecordLogEntry` persists via the exported `persistLogEntry` — deliberately **not** via `log()`, which would also console the message a second time (the content script already consoles its own message directly into the *page's* devtools, a separate console from the background service worker's). `shared/logSerialize.ts`'s `serializeLogDetail` (moved out of `background/logging/handler.ts`, pure/no-I/O) is shared by both sides so a `LogEntry.detail` round-trips identically regardless of which one wrote it — same reasoning as this repo's earlier `passwordGenerator.ts` move to `shared/`.
- **New call sites trace one representative, fully end-to-end flow** (content script → `background/router/dispatch.ts` → `background/formDetection/handler.ts` → `background/policy/autoApply.ts` / `background/firewall/handler.ts`'s `resolvePolicy` call sites → `handleSubmitFieldDecisions`), deliberately **not** every handler in the codebase (CLAUDE.md's "layers long, not wide") — `vault/personalData`, `vault/credentials` (including `handleFormSubmitted`'s credential-capture path, which sits in the same file as `handleFormDetected` but handles real password/identifier values), backup/restore, and identity creation are explicitly deferred to a mechanical follow-up once this pattern is proven. `background/router/dispatch.ts` is the one universal chokepoint every message already passes through, so its own two new `'info'` calls (message received / handler resolved) give every present and future message type basic tracing for free, without touching each handler individually.
- **Never logs an actual disclosed/personal-data value.** Every new call site logs the *decision* (`fieldType`, `PolicyAction`/`ResponseType`, booleans, counts, `origin`) never the *value* — checked against `shared/vault-schema.ts`'s sensitivity levels (`nationalId` is the one `highlySensitive`, always-ask field) and the existing "real value" variables in `firewall/handler.ts`/`firewall/responseGenerator.ts`/`vault/personalData/handler.ts`/`vault/credentials/handler.ts`. The single highest-stakes line is `firewall/handler.ts`'s per-field `'debug'` call inside `handleSubmitFieldDecisions`, three lines from `generateResponseValue`'s real return value — logs `disclosed: value !== null`, never `value`.
- **Color mapping** (`entrypoints/options/App.vue`'s `logLevelClasses`): `'error'` → `if-tangerine` (unchanged), `'debug'` → `if-lagoon` (unchanged — stays the calmest color since debug-tagged entries are the highest-frequency once per-field policy logging is in the mix), `'info'` → **`if-sunbeam`** (new — a warm gold, "notable, not alarming"). `if-blue` deliberately not reused (already this page's primary interactive-accent color elsewhere); `if-dahlia` stays unclaimed (a natural fit for a future `'warn'` level).
- **Verbosity control UI**: the boolean `UiToggle` became a native `<select>` (Off/Info/Debug (verbose)), mirroring `autoLockSelectValue`'s own existing get/set-computed pattern in the same file rather than introducing a new component for a 3-way choice.

## Known limitations

- `wxt/testing/fake-browser` does not implement/fire `storage.onChanged` (confirmed by inspecting its source — no matches for `onChanged` anywhere in the package), so the live-update wiring itself has no unit-test coverage and relies on manual verification only. Matches this codebase's existing precedent for fake-browser gaps (`chrome.idle` is the other one, called out in `autolock-and-configuration.md`).
- **Content-script log data is less developer-controlled than every other call site.** Every pre-existing `log()` call passes a fixed, developer-authored string with a caught `Error` as detail; `RECORD_LOG_ENTRY`'s payload originates in `content/log.ts`, which is extension code, not page code, but its two call sites in `entrypoints/content.ts` are kept deliberately limited to counts/booleans/`formIndex` — never a raw string sourced from the page's own DOM (a form's `action`, a field's `name`/`id`) — so a hostile page can't smuggle arbitrary content into the persisted log through it.
- **Ring-buffer flooding is a pre-existing, accepted property, now more likely to matter.** The 500-entry cap (`MAX_LOG_ENTRIES`, `background/logging/storage.ts`) is shared across every source — background and every open tab's content script. Once `'debug'`-level per-field policy/response logging is in the mix, a busy session (many tabs, many forms) can evict older entries — including `'error'`-tagged ones — sooner than before. No rate limit is added preemptively; a future per-source limit in `persistLogEntry` is a deliberate non-goal for now.

## Implementation

- `background/logging/storage.ts` — `getLogEntries()`/`appendLogEntry()`/`clearLog()`, guarded by `createSerialQueue()` (`background/vault/serialQueue.ts`) for race-free appends.
- `background/logging/handler.ts` — `log(level, message, detail?)`, the one function the rest of `background/` calls instead of a bare `console.debug`/`console.error`/`console.info`: unchanged console output, plus a fire-and-forget, never-throwing persist gated on the `logLevel` threshold (`shouldPersist()`). Exports `persistLogEntry` for `handleRecordLogEntry` (the `RECORD_LOG_ENTRY` handler) to call directly, bypassing `log()`'s own console call. Also `handleGetLogs`/`handleClearLogs`.
- `shared/messages.ts` — `LogLevelSchema`/`LogLevel` (now schema-first), `LogEntry`, `GET_LOGS`/`CLEAR_LOGS`/`RECORD_LOG_ENTRY` message schemas.
- `shared/settings.ts` — `LogThresholdSchema`/`LogThreshold`, `AppSettingsSchema.logLevel`.
- `shared/logSerialize.ts` (new) — `serializeLogDetail`, shared by `background/logging/handler.ts` and `content/log.ts`.
- `content/log.ts` (new) — `reportLog(level, message, detail?)`.
- `background/router/registry.ts` — the `'logging'` capability now also routes `RECORD_LOG_ENTRY`.
- Retrofitted 5 original `console.debug`/`console.error` call sites to route through `log()`: `background/badge.ts`, `background/vault/credentials/autoSaveNotice.ts`, `background/settings/handler.ts`, `background/settings/idleLock.ts` (×2). New tracing call sites added along the Content Script → Policy Engine → Firewall flow: `entrypoints/content.ts` (×2, via `reportLog`), `background/router/dispatch.ts` (×4), `background/formDetection/handler.ts`'s `handleFormDetected` (×2), `background/policy/autoApply.ts` (per-field), `background/firewall/handler.ts` (per-field ×2, lifecycle ×2).
- `stores/logs.store.ts` — `fetchLogs()`/`clear()`/`exportLogs()`, mirroring `stores/appSettings.store.ts`'s shape; `exportLogs()` adapts `stores/vault.store.ts`'s `downloadBackupBundle` Blob/anchor-click pattern for plain text instead of JSON.
- `entrypoints/options/App.vue`'s Configuration tab — a "Local dev log" verbosity `<select>` (Off/Info/Debug), and a "Logs" card (currently laid out as a secondary right-hand column alongside the other Configuration cards) with the `VaultLockedNotice` gate, entry-count summary, the live palette-colored entry list, Clear button, and the Download-with-re-confirmation flow.

## Verification

- `pnpm check` — unit tests for `background/logging/storage.ts` (append/trim-at-500/clear/concurrent-append ordering), `background/logging/handler.ts` (console passthrough, all 3 threshold branches, `handleRecordLogEntry` persists without double-consoling, never throws on a storage failure, `Error` details serialize to their stack/message), and `content/log.ts` (`reportLog` sends the right message shape, omits `detail` when absent, never throws on a rejected transport).
- No `pnpm test:e2e` (standing user preference — e2e is run manually).
- Manually verified (original pass): toggling logging off/on, triggering a real failure path (Firefox's benign `browser.action`-vs-`browser.browserAction` badge error), unlocking the vault and seeing a real entry count, downloading a real `.log` file via the re-confirmation form, and watching the entry list update live (no manual refresh) while a real failure path fired repeatedly with the Configuration tab already open.
- Manual verification still needed for this expansion (by the user): set the level to Debug, load one of the `tests/manual/` fixture pages (`signup.html`/`login.html`), submit a form, and confirm the Options tab's live Logs list shows the traced flow (form detected → dispatch received/resolved → classification → per-field policy decisions → firewall applied decisions) with plausible, non-sensitive detail; confirm Off truly persists nothing; confirm Info shows only the lifecycle events, without the per-field noise.
