# Research: Email Alias Provider Integration (SimpleLogin vs addy.io)

## Purpose

`docs/competitive-landscape.md` already made the call: **do not build our own email/SMTP/DKIM/DMARC alias infrastructure — integrate with an existing self-hostable alias provider.** This document turns that decision into a concrete integration plan by researching the actual public APIs of the two candidates named there, SimpleLogin and addy.io, and by checking a load-bearing assumption of our local-first model: that using these providers does not reintroduce a dependency on infrastructure *we* run.

Everything below is either (a) a direct finding from a cited primary source, or (b) explicitly marked as unverified/inferred where I could not confirm it from documentation.

---

## 1. SimpleLogin's public API

**Primary source:** [`docs/api.md` in `simple-login/app`](https://github.com/simple-login/app/blob/master/docs/api.md) (the project's own repo — this is the closest thing to canonical API documentation SimpleLogin has; there is no separate hosted API-reference site distinct from this file). Fetched via the raw file at `raw.githubusercontent.com/simple-login/app/master/docs/api.md`.

### Authentication

- A per-user **API key** ("api code") is sent in an `Authentication` request header on almost every call.
- Confirmed quote: *"the client includes the `api code` in `Authentication` header in almost all requests."*
- The key is generated by the user from their own SimpleLogin account (hosted or self-hosted) — it is not something our extension provisions on the user's behalf.

### Creating an alias — two paths

**Random alias (the one relevant to our MVP flow):**
- `POST /api/alias/random/new`
- Query string: `hostname` (optional but recommended), `mode` (optional: `uuid` or `word` — controls the shape of the random local-part)
- Body: `note` (optional, free text)
- Response: `201` with the new alias's info, same shape as `GET /api/aliases/:alias_id`
- **The alias itself is not user-specified in this path** — SimpleLogin generates the local-part. This is the "click one button, get an alias" flow used by SimpleLogin's own browser extension.

**Custom alias (user picks the local-part):**
- `GET /api/v5/alias/options` first, to fetch `can_create` (boolean — can this user create more aliases, relevant to free-tier caps), the list of allowed `suffixes`, and a `signed_suffix` per suffix (a server-signed token — *"necessary to avoid request tampering"*, per the docs).
- `POST /api/v3/alias/custom/new` with `alias_prefix` (the chosen local-part), `signed_suffix` (must be one from the options call — you cannot invent your own domain/suffix), `mailbox_ids` (required — list of mailbox IDs that "own" this alias), and optional `note`/`name`.
- Query string: `hostname` (optional but recommended, same as above).

**On the "note"/"mailbox" scoping question asked in the task:** confirmed — both alias-creation endpoints accept a **`note`** field for free-text tagging, and the custom-alias endpoint additionally requires binding the alias to one or more **mailboxes** (`mailbox_ids`, i.e. which real inbox the forwarded mail lands in — not a per-site tag). For our purposes, `note` is the right field to stamp with something like `Identity Firewall — github.com`, and the documented purpose of the `hostname` query parameter is exactly this use case: *"This information is important to know where an alias is used in order to suggest user the same alias if they want to create on alias on the same website in the future."* So SimpleLogin already has a first-class, documented concept of "which site is this alias for" via `hostname` — we don't need to invent our own tagging convention, though we should still also write the mapping into our own `ServiceIdentity` record so it's queryable without calling SimpleLogin's API.

### List / get / delete / disable

- `GET /api/v2/aliases` — list the user's aliases, paginated (`page_id` query param).
- `GET /api/aliases/:alias_id` — get one alias's detail (id, email, name, `enabled`, creation timestamp, `note`, forward/block/reply counters, mailboxes, latest activity, pinned).
- `POST /api/aliases/:alias_id/toggle` — flips `enabled`; response `{"enabled": bool}`. This is the "disable" operation — SimpleLogin models disable as a toggle, not a separate disable/enable pair of endpoints.
- `DELETE /api/aliases/:alias_id` — permanent delete; response `{"deleted": true}`.
- `PATCH /api/aliases/:alias_id` — update `note`, `mailbox_id`/`mailbox_ids`, `name`, `disable_pgp`, `pinned`.

### Rate limits

- **Not documented as fixed numbers.** SimpleLogin uses `flask-limiter` internally and returns HTTP `429` with a "Rate limit exceeded" body when triggered (confirmed via real-world `429` errors reported against `POST /api/v3/alias/custom/new` in the wild, and via a maintainer comment in a GitHub Discussion that the limit "is there to avoid abuses and its setting can be changed in the SaaS version anytime" — i.e. it's an implementation detail, not a published contract).
- **Implication for us:** treat rate limits as unknown/variable. Our Alias Manager should handle `429` with backoff and a user-visible "try again" rather than assuming a specific quota.

Sources:
- [`simple-login/app` — `docs/api.md`](https://github.com/simple-login/app/blob/master/docs/api.md) (primary; fetched directly)
- [GitHub Discussion #623 — "What's the rate limit?"](https://github.com/simple-login/app/discussions/623) — maintainer response, no fixed number given
- [GitHub Discussion #1634 — alias custom new API](https://github.com/simple-login/app/discussions/1634) — confirms real-world usage of the signed-suffix flow

## 2. Self-hosting reality check (SimpleLogin)

Confirmed from multiple sources (project's own deployment docs, and third-party self-hosting write-ups referencing them):

- Self-hosted SimpleLogin is a **multi-service backend**, not a single binary: a Postgres database (12.1+/13+ depending on doc version), the SimpleLogin web/API app itself, and a **real mail-receiving stack** — MX records, SPF, DKIM (the docs specifically call out generating a DKIM keypair), DMARC, and open inbound SMTP ports (25, 465, 587) on a server with a static IP and PTR/reverse-DNS record matching a domain you own.
- This is exactly the "full SMTP/DNS/DKIM/DMARC infrastructure" our own `competitive-landscape.md` already flagged as out of scope for us to build — and it's equally out of scope for a typical end user to stand up for themselves.

**Explicit answer to the reality-check question:** self-hosting SimpleLogin is **not realistic for an individual end user of our extension.** It requires owning a domain, running a Postgres+Docker stack continuously, opening SMTP ports on a public IP, and maintaining DNS/DKIM/SPF/DMARC correctly (misconfiguration here silently breaks deliverability, which is a security-relevant failure mode — mail silently not arriving). This is systems-administration work comparable to running your own mail server, because it *is* running your own mail server. It only makes sense for:
- A technically sophisticated user who already runs their own infrastructure and wants full independence, or
- Us (or a community member) running one shared instance for multiple users to point at — which reintroduces a "trust a server" relationship, just with a different, smaller operator than us.

**Why the hosted SimpleLogin.io service is still consistent with our local-first philosophy, and this distinction must be precise in our docs:**

| | Our own backend (rejected) | Hosted SimpleLogin.io / addy.io (what we'd integrate) |
|---|---|---|
| Who runs it | Us | A third-party OSS project, chosen and configured by the user |
| Is it mandatory | Would be, if built | No — entirely optional, user opts in |
| What we store | Nothing of the user's mail | Nothing — we never see their SimpleLogin account beyond the API key they gave us |
| Trust relationship | User forced to trust *us* | User explicitly chooses to trust *SimpleLogin the project* (or self-hosts it, or runs neither) |
| Consistent with ADR-007 (no server dependency)? | No — violates it directly | Yes — *our* product has zero server; the alias feature is an optional client of a service the user picked, exactly like a user choosing to sync passwords through their own Nextcloud |

This is the same shape as "the vault is local-first, but the user may optionally use their own cloud storage for backup" — the optionality and user-choice are what keep it consistent with ADR-007, not the absence of any third party anywhere in the picture. Our docs (`docs/architecture.md` / ADR-007) should state this distinction explicitly so it isn't mistaken for a loophole: **zero dependency on infrastructure *we* control is non-negotiable; a dependency the user *deliberately and individually* opts into, pointing at infrastructure *they* chose (hosted or self-hosted), is a different and acceptable relationship.**

Sources:
- [`self-hosted-simplelogin` (springcomp), DNS/DKIM/MX/ports write-up](https://github.com/springcomp/self-hosted-simplelogin)
- [DeepWiki — Self-Hosting Deployment Guide, simple-login/app](https://deepwiki.com/simple-login/app/10.4-self-hosting-deployment-guide) (secondary/derived source, cross-checked against the primary repo's own deploy docs — flagged here as such since DeepWiki is an AI-generated wiki, not SimpleLogin's own text)
- [tinker.expert — "Self-hosting SimpleLogin: own your email aliases for $3 a month"](https://tinker.expert/blog/self-hosting-simplelogin) (third-party account confirming the domain+VPS+DNS requirement in practice)

## 3. addy.io's API

**Primary source:** [`app.addy.io/docs/`](https://app.addy.io/docs/) (addy.io's own hosted API reference) and [`addy.io/help/api-settings/`](https://addy.io/help/api-settings/).

### Authentication

- Bearer token: `Authorization: Bearer {API_KEY}` header, on every request.
- Base URL: `https://app.addy.io` (or the user's own self-hosted instance's URL).
- The user generates the API key themselves from Account Settings → API, same "one-time setup, done by the user" shape as SimpleLogin.

### Creating an alias

- `POST /api/v1/aliases`
- Body parameters: `domain` (required — which of the user's available alias domains to use), `format` (optional: `random_characters`, `uuid`, `random_words`, `random_male_name`, `random_female_name`, `random_noun`, or `custom`), `local_part` (required only if `format` is `custom` — this is addy.io's equivalent of SimpleLogin's `alias_prefix`), `description` (optional free text — addy.io's equivalent of SimpleLogin's `note`), `recipient_ids[]` (optional, which of the user's verified inboxes receive it — equivalent of SimpleLogin's `mailbox_ids`), `label_ids[]` (optional — addy.io additionally supports arbitrary labels/tags on aliases, which SimpleLogin does not have as a first-class concept beyond free-text `note`).
- Response: `201` with the alias object.
- **Notably, unlike SimpleLogin, addy.io does not have a documented `hostname` query parameter** on alias creation — there's no built-in "which website is this for" concept in the create call itself. `description` (or the newer `label_ids`) is the closest fit, meaning **we would own the site-association convention ourselves** rather than leaning on a provider-native field, if we integrate addy.io.

### List / get / delete / activate-deactivate

- `GET /api/v1/aliases` — list, with `filter[deleted]`, `filter[active]`, `filter[pinned]`, `filter[label]`, `filter[search]`, and `page[number]`/`page[size]` (max 100) pagination.
- `GET /api/v1/aliases/{id}` — single alias.
- `DELETE /api/v1/aliases/{id}` — `204 No Content`.
- `POST /api/v1/active-aliases` (body `{"id": ...}`) to activate / `DELETE /api/v1/active-aliases/{id}` to deactivate — addy.io's equivalent of SimpleLogin's enable/disable toggle, but split into two endpoints instead of one toggle.
- Bulk variants exist (`.../activate/bulk`, `/deactivate/bulk`, `/delete/bulk`, `/restore/bulk`, max 25 ids per call) — useful if a user ever wants to bulk-revoke aliases from our UI, which SimpleLogin's documented API does not appear to offer as a batch operation.

### Rate limits

- **Not documented with fixed numbers** in the public docs I could access. Flagged as **unverified** — I did not find an equivalent of SimpleLogin's GitHub Discussion threads confirming `429` behavior for addy.io specifically; treat it the same defensive way (handle `429`/`5xx` with backoff) until proven otherwise.

### Self-hosting (addy.io)

Confirmed similarly heavy: requires your own domain, a Postfix MTA piping mail into the app, MySQL, DKIM key generation, reverse-DNS/PTR records pointing at a `mail.example.com`-style hostname, and Docker Compose orchestration (official image at `github.com/anonaddy/docker`). Same verdict as SimpleLogin: **not realistic for an average end user to self-host; realistic only for a technical user or an organization running a shared instance.**

Sources:
- [addy.io API Documentation](https://app.addy.io/docs/) (primary)
- [addy.io — API Settings help page](https://addy.io/help/api-settings/)
- [addy.io — How to self-host addy.io](https://addy.io/self-hosting/) (primary, addy.io's own self-hosting guide)
- [`anonaddy/docker` GitHub discussion #277 — Docker deployment specifics](https://github.com/anonaddy/docker/discussions/277)

### SimpleLogin vs addy.io — which is simpler to integrate

| | SimpleLogin | addy.io |
|---|---|---|
| Auth | `Authentication: <key>` header | `Authorization: Bearer <key>` header (more conventional/standard) |
| One-call random alias | Yes — `POST /api/alias/random/new`, no domain param needed (uses account default) | Requires knowing/passing a `domain` even for random formats |
| Native "which site is this for" field | Yes — documented `hostname` query param, purpose-built for this | No — must overload `description` or `label_ids` ourselves |
| Enable/disable model | Single toggle endpoint | Two endpoints (activate/deactivate) — marginally more calls to wire up |
| Custom alias flow | Two-step (fetch signed suffix, then create) — more ceremony | One-step (`format: custom`, `local_part`) — simpler |
| Bulk operations | Not documented | Yes, documented bulk activate/deactivate/delete/restore |
| API documentation quality | Good, but living only as a Markdown file in the repo, not a dedicated reference site | Good, and has an actual hosted docs site (`app.addy.io/docs`) with a "new API" (i.e., actively maintained, versioned) |

**Net assessment:** for the one flow our MVP actually needs — *"user approves an alias response for an email field, we get back a working forwarding address with minimal ceremony"* — **SimpleLogin's `POST /api/alias/random/new` is the simplest single call of the two**, and it uniquely offers the `hostname` field that matches our exact use case (per-site alias tagging) without us inventing a convention. addy.io is comparable and has nicer bulk operations and a more conventional Bearer-auth scheme, but requires us to pass an explicit `domain` and to own the site-tagging convention ourselves via `description`.

## 4. Concrete integration sketch

This assumes the **Alias Manager** component named in `docs/browser-architecture.md`'s legacy-web pipeline (step 6, "Credential/Alias generation") is the piece responsible for this call — it sits in the Background Service, invoked by the Policy Engine once the user (or an existing per-site policy) has approved an "alias" response for an email field.

### User-provided configuration (one-time setup)

- In the extension's Settings UI, an optional "Email Alias Provider" section lets the user:
  1. Pick a provider: **None (default) / SimpleLogin / addy.io**.
  2. Paste their own API key, generated from their own account (hosted SimpleLogin.io / app.addy.io, or their own self-hosted instance's URL + key).
  3. Optionally override the API base URL, to support self-hosted instances (`https://mysimplelogin.example.com/api` instead of `https://app.simplelogin.io/api`).
- This API key is stored **in the same encrypted local vault as everything else** (per `docs/data-model.md`'s `Policies`/config area, or a new small `AliasProviderConfig` leaf next to `Aliases`) — it is never transmitted to any server of ours, because we have none. It is only ever sent, over HTTPS, directly from the user's browser to the alias provider's API (their own chosen server, hosted or self-hosted) — exactly the pattern the `Password` field of a normal password manager entry already follows.

### Pseudocode — SimpleLogin path (recommended first integration)

```text
// Alias Manager, invoked by Policy Engine when an email field
// is approved with response type = "alias" for origin `site`

async function getOrCreateAliasFor(serviceIdentity, site):
    config = vault.read("AliasProviderConfig")
    if config.provider == "none":
        return null   // caller falls back to synthetic/deny — see §5

    existing = serviceIdentity.aliases.find(a => a.provider == config.provider
                                                  && a.field == "email")
    if existing:
        return existing.value   // reuse — don't mint a new alias every visit

    response = httpPost(
        url: `${config.baseUrl}/api/alias/random/new`,
        headers: { "Authentication": config.apiKey },
        query: { hostname: site.hostname, mode: "word" },
        body: { note: `Identity Firewall — ${site.hostname}` }
    )

    if response.status == 429:
        return retryWithBackoff(...)   // rate-limited, don't hammer the API
    if response.status != 201:
        notifyUser("Alias creation failed, falling back")
        return null

    alias = response.body   // { id, email, enabled, note, ... }

    serviceIdentity.aliases.push({
        provider: "simplelogin",
        providerAliasId: alias.id,
        field: "email",
        value: alias.email,
        createdAt: now(),
        note: alias.note
    })
    vault.write(serviceIdentity)
    privacyLedger.record(site, field: "email", response: "alias", value: alias.email)

    return alias.email
```

### Revocation path (from our "what does this site know about me?" UI)

```text
async function revokeAliasFor(serviceIdentity, aliasEntry):
    config = vault.read("AliasProviderConfig")
    httpDelete(
        url: `${config.baseUrl}/api/aliases/${aliasEntry.providerAliasId}`,
        headers: { "Authentication": config.apiKey }
    )
    serviceIdentity.aliases.remove(aliasEntry)
    vault.write(serviceIdentity)
    privacyLedger.record(site, action: "alias revoked")
```

### addy.io path differs only in the request shape

```text
response = httpPost(
    url: `${config.baseUrl}/api/v1/aliases`,
    headers: { "Authorization": `Bearer ${config.apiKey}` },
    body: {
        domain: config.defaultDomain,   // must be configured/fetched up front
        format: "random_words",
        description: `Identity Firewall — ${site.hostname}`
    }
)
```

The two providers' request/response shapes are close enough that a single internal `AliasProvider` interface (`createAlias(site) -> {id, email}`, `deleteAlias(id)`, `toggleAlias(id, enabled)`) can front either one, with a thin per-provider adapter — this is the shape our Alias Manager should be built around from the start so adding the second provider later is a small adapter, not a rewrite.

### Local-first check

- No data flows through any server we operate — there isn't one.
- The only network call this feature ever makes is the user's own browser talking directly to the alias-provider endpoint the user configured (default hosted SimpleLogin.io/addy.io, or their own self-hosted URL).
- If the user never configures a provider, this code path is never invoked (see §5) — the feature is additive, not load-bearing for the rest of the product.

## 5. Fallback / graceful degradation

Confirmed from our own docs:

- `docs/roadmap.md` Phase 6 already lists "Optional integration with SimpleLogin/addy.io" as an *objective* of Legacy Web Compatibility, phrased as optional, not a hard MVP requirement — the phase's core objectives (traditional login/signup, controlled autofill, unique password per service, compatibility across form structures) do not depend on it.
- `docs/data-model.md`'s response-type table already defines **Alias** as one of five response types alongside **Real, Synthetic, Nonsense, Deny** — meaning the data model was already designed assuming alias is one option among several, not the only way to handle an email field. A user with no alias provider configured can still get a **Real** email, a **Synthetic**-looking placeholder (with the same legal caveat already documented — never for contexts requiring a real, legally binding value), or **Deny**.
- **Confirmed:** the existing docs already treat email-aliasing as optional/pluggable. No change of principle is needed here — this research only firms up *how* "optional" is implemented (a `provider: none` default state in `AliasProviderConfig`, with the Policy Engine's default "email → alias" rule falling back to prompting the user for Real/Synthetic/Deny when no provider is configured, rather than silently failing).

**Recommended addition to `docs/data-model.md`:** the default policy table currently says email's default behavior is "Alias" unconditionally. It should be qualified: *"Alias, if an alias provider is configured; otherwise fall back to Ask."* This is a small precision fix, not a redesign.

## Implications for our design

### Provider recommendation: integrate SimpleLogin first

Reasons, in order of weight:

1. **The single most common flow our MVP needs — mint a random alias for an email field, tagged to the site — is a one-step, one-parameter-set call for SimpleLogin (`POST /api/alias/random/new?hostname=...`) with a provider-native field for exactly the "which site" tagging we need (`hostname`).** addy.io requires us to already know/configure a `domain` and to invent our own site-tagging convention via `description`.
2. SimpleLogin is the one already named specifically in `docs/competitive-landscape.md` as the closer study target (its own browser extension is cited as prior art), so our team already has more context on it.
3. Both are comparably self-hostable-but-not-user-friendly-to-self-host, so this doesn't differentiate them — see §2.
4. addy.io is still worth a second adapter soon after, given its cleaner Bearer auth and native bulk-revoke operations — the `AliasProvider` interface sketched in §4 is designed so this is incremental, not a rewrite.

**Core API call shape for the MVP (SimpleLogin):**

```
POST https://app.simplelogin.io/api/alias/random/new?hostname={site}&mode=word
Authentication: {user's own API key}
Body: { "note": "Identity Firewall — {site}" }
→ 201 { id, email, enabled, note, ... }
```

### Changes recommended to other docs (not made here — out of scope for this file, flagged for follow-up)

- `docs/data-model.md`: qualify the email default policy ("Alias, if configured; otherwise Ask") and consider adding `provider`, `providerAliasId`, and `note`/`hostname` fields explicitly to the `Aliases` entry shape, since those are the fields the real APIs actually return/require and our `ServiceIdentity.aliases` entries will need to round-trip them for later revocation/toggling.
- `docs/roadmap.md` Phase 6: no change of scope needed — "optional integration with SimpleLogin/addy.io" already correctly frames this as additive. Could optionally note SimpleLogin as the first target and addy.io as the fast-follow, per the recommendation above.
- `docs/architecture.md` / `ADR-007-no-server-dependency.md`: worth adding the explicit "our-server vs. user's-own-chosen-third-party-server" distinction laid out in §2 of this document, so a reader doesn't mistake "integrates with a hosted SaaS API" for a violation of the no-server-dependency principle.
